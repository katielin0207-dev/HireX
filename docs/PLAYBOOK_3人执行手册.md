# 第零部分：开工前准备（冲刺开始前一天完成）

## 0.1 队长（A）做的事

**第一步：把项目推上 Git 仓库**（10 分钟）

```bash
cd /Users/admin/WorkBuddy/2026-08-14-08-35-52/AI-recruitment-system

git init
git add .
git commit -m "chore: 基座项目 + A开工包（契约/公共件/Mock数据）"

# 在 GitHub 建一个 Private 仓库（比如叫 recruit-mvp），然后：
git remote add origin git@github.com:你的账号/recruit-mvp.git
git branch -M main
git push -u origin main
```

**第二步：邀请队友进仓库**
GitHub 仓库页面 → Settings → Collaborators → 输入队友 GitHub 账号。

**第三步：私发敏感信息（不要提交到仓库！）**
把 `.env` 的内容（主要是 DeepSeek API Key）通过微信/私信单独发给两个队友。
⚠️ `.env` 已在 `.gitignore` 里，不会被提交，这是对的——Key 不能进 Git 历史。

## 0.2 两个队友（B、C）做的事

**第一步：克隆项目**（5 分钟）

```bash
git clone git@github.com:你的账号/recruit-mvp.git
cd recruit-mvp
```

**第二步：配置 API Key**（2 分钟）

```bash
cp .env.example .env
# 用编辑器打开 .env，把 LLM_API_KEY= 后面替换成 A 私发给你的 Key
```

**第三步：一键启动验证**（首次 5-10 分钟，装依赖）

```bash
chmod +x dev.sh
./dev.sh
```

看到 `http://127.0.0.1:8501` 打开浏览器能出界面 = 环境 OK。
如果报错，截图发到群里@A。

**第四步：跑通共享件自测**（3 分钟）

```bash
.venv/bin/python -c "
import sys; sys.path.insert(0, '.')
from app.shared import load_jd, list_candidates, call_llm
print('JD:', load_jd()['title'])
print('候选人:', [c['name'] for c in list_candidates()])
print('LLM测试:', call_llm('回复ok两个字', expect_json=False))
"
```

三行都有正常输出 = 开工包在你的机器上完全可用。

# 第一部分：三人分工（替代原 5 人方案）

| 人 | 角色 | 负责模块 | 负责文件 |
|----|------|---------|---------|
| **A** | 基建 + 简历筛选 | ①速度优化（生死线）②简历筛选模块 ③导航注册+三次合并 ④演示缓存预跑 | `app/views/screening.py`、`app/rule_engine.py`、`app/main.py` |
| **B** | 风险识别 + 面试辅助 | ①风险识别引擎+页面 ②面试评价表生成 | `app/risk_engine.py`、`app/views/risk.py`、`app/evaluation.py`、`app/views/interview_eval.py` |
| **C** | 人才评价 + 集成测试 + 演示 | ①人才对比+人才库 ②全流程联调测试 ③演示数据+彩排 | `app/talent_pool.py`、`app/views/talent.py`、`tests/test_e2e.py` |

**分工逻辑**：A 的基建活已经在我（AI）帮助下完成了一大半（公共件/Mock/模板），所以 A 有余力承担最大的业务模块（简历筛选）；B 的两个模块都是"引擎+页面"同构型，写起来模式一致最快；C 的人才评价是纯数据聚合展示、无 LLM 深度依赖，最早完成后正好接联调和演示准备。

**⚠️ 重要架构决策（三人必读）**：
基座项目自带的分析管线（Graph DAG 那套）跑一份简历要 20 分钟，**演示不能用**。所有新模块**不要调用基座的 pipeline**，直接用 `call_llm` 写轻量管线：

- 筛选：1 次 LLM 调用 = 解析+评分（一个 Prompt 合并干完）
- 风险：1 次 LLM 调用 = 五维扫描
- 评价：1 次 LLM 调用 = 笔记→评价表

基座的 `matcher.py`、`prompts.py` 里的 **Prompt 可以抄**，管线不要抄。

# 第二部分：24 小时逐小时流程

## 第 0 小时｜开工会（45 分钟，全员语音）

| 时间 | 内容 | 产出 |
|------|------|------|
| 0:00-0:10 | 全员默读 `docs/CONTRACT.md` | — |
| 0:10-0:25 | A 讲解：契约字段、公共件用法、模板页结构（对着 `app/views/_template.py` 讲） | 三人都知道怎么写页面 |
| 0:25-0:35 | 确认分工 + 过一遍本手册的里程碑 | 无异议 |
| 0:35-0:45 | 各自拉分支：`git checkout -b feat/screening`（A）/ `feat/risk-interview`（B）/ `feat/talent`（C） | 三条分支 |

**开工会后立即群发**：演示脚本（见第五部分），每个人知道自己模块在演示第几分钟出场。

## 第 1-3 小时｜A 的速度生死线 + B/C 启动

**A（速度优化，最重要！）**：
1. 写 `app/rule_engine.py`：硬性条件评分用纯代码（学历/年限/技能覆盖度），不写一行 LLM 调用。这是 POC 发现"学历分波动±15"的修复方案
2. 写 `app/views/screening.py` 的批量管线骨架：
   - 读 `mock/resumes/` 10 份简历
   - `map_llm` 并发 3，每份简历**一次** LLM 调用完成"解析+软性评分"
   - 硬性分 = rule_engine 算，软性分 = LLM 算，总分 = 硬 60% + 软 40%
3. 目标：**10 份简历批量分析 ≤ 90 秒**

**B（风险引擎启动）**：
1. 写 `app/risk_engine.py`：
   - 规则部分：时间线断层检测（解析日期算间隔）、跳槽频率计算（经历段数/年限）、证书过期比对（当前日期 vs 有效期）——**这三维纯代码，确定性**
   - LLM 部分：一次调用做"信息存疑+技能存疑"判断（喂简历原文，要求引用证据）
   - 输出按契约 `risk_report` 结构
2. 用 `cand_003`（马跃，经历断层）自测：必须识别出 2022.01-2024.05 空档

**C（人才评价启动 + 环境保障）**：
1. 写 `app/views/talent.py`：读 `list_candidates()`，渲染对比表（姓名/总分/风险等级/状态）
2. 装 plotly（基座已装）画雷达图雏形：选 2-3 个候选人，维度分对比
3. 顺手验证：A 的批量管线跑完后候选人 JSON 字段是否完整（第一个集成测试）

**第 3 小时末·群里打卡**：每人发一句话进度 + 卡点（格式：`[进度] 完成XX，正在XX [卡点] 无/有`）

## 第 4-6 小时｜功能成型

**A**：
- 筛选页面完成：简历列表 → 批量分析按钮 → 进度条（`st.status`）→ 排名表（总分/硬性/软性/推荐结论，按总分排序）
- 排名表每行可展开看匹配报告（matched_points / gap_points / summary）

**B**：
- `app/views/risk.py` 页面完成：候选人下拉 → 风险分析 → 报告展示（等级 badge + 风险列表 + 面试关注点）
- 用 3 个 Mock 候选人全测一遍：马跃必须高风险、陈晓必须低风险

**C**：
- 雷达图完成（plotly，维度：技能/经验/学历/项目）
- 人才库列表页：按 status 过滤、按 tags 展示
- 开始写 `tests/test_e2e.py`：模拟全流程（导入简历→筛选→风险→评价→对比）的断言脚本

## 第 6 小时｜第一次合并（30 分钟）

```bash
# A 执行：
git checkout main
git merge feat/screening
git merge feat/risk-interview
git merge feat/talent
# 有冲突就三方现场解决（大概率没有，因为文件隔离）
git push
```

**合并后全员**：`git checkout 自己的分支 && git merge main`，继续开发。
**检查点 M1**：A 演示批量筛选跑通（90 秒内），B 演示风险报告（马跃=高风险），C 演示对比表能显示数据。任何一人没跑通 → 接下来 2 小时优先修通，砍次要功能。

## 第 7-10 小时｜功能补全

**A**：
- JD 编辑页：textarea 改 JD → `save_jd()` → 重新分析按钮
- 开始写导航：把 B、C 的页面函数注册进 `app/main.py`（B/C 此时应已把函数名报给 A）

**B**：
- 面试评价模块 `app/evaluation.py` + `app/views/interview_eval.py`：
  - 页面：选候选人 → 大文本框粘贴"面试记录" → 生成评价表
  - 一次 LLM 调用：面试记录 + 该候选人的 match_result + risk_report 一起喂进去 → 输出 `interview_eval`（rating/维度分/总结/关注点）
  - 评价表可编辑（`st.data_editor` 或 text_area 回显）→ 确认后 `update_candidate`

**C**：
- "放弃 offer 推备选"功能：候选人状态改为 `declined` 时，自动列出同岗位其他候选人按总分排序
- `test_e2e.py` 跑通基础断言（至少：筛选后 JSON 有 match_result、风险后有 risk_report）

**第 10 小时·站会（15 分钟）**：过 M2 前的收尾项，明确剩余 4 小时每人具体做什么。**决定：哪些功能砍掉**（砍单顺序：人才库标签编辑 → 评价表在线编辑 → 雷达图美化）。

## 第 10 小时｜第二次合并（30 分钟）

同第 6 小时流程。合并后跑 `./dev.sh`，**主链路首次端到端走一遍**：
导入简历 → 批量筛选 → 风险报告 → 面试评价 → 人才对比。
此时允许有 bug，记录下来分工修。

## 第 11-14 小时｜联调修 bug + A 预跑演示缓存

**A**：
- 修完自己的 bug 后，做**演示模式预跑**（生死线）：
  - 用最终演示数据（1 JD + 10 简历）完整跑一遍
  - 把每步结果存缓存：`save_demo_cache("screening", 排名表)`、`save_demo_cache("risk_马跃", 报告)`、`save_demo_cache("eval_陈晓", 评价表)`、`save_demo_cache("talent", 对比数据)`
  - 提交 `mock/demo_cache/` 到 git（这是演示翻车保险）

**B**：修 bug + 准备演示用的"面试记录"文本（200-300 字，模拟一场真实面试的问答记录，含亮点和瑕疵，让 AI 生成的评价表有看头）

**C**：
- `test_e2e.py` 全绿
- 写演示脚本提词卡（每步点哪里、说什么、预期画面是什么）
- 和 A 对一遍演示数据的"故事线"：陈晓（第一名，推进）→ 马跃（高风险，刷掉）→ 孙强（备选，第一名放弃后顶上）

## 第 14 小时｜第三次合并 + M2 检查点（1 小时）

合并后完整走演示流程一遍（用真实 API）：
- ✅ 顺利 → 用**满配演示**（四模块全链路）
- ❌ 卡顿/失败 → 切**保底演示**（脊柱链路：筛选+评分+出题，其余模块展示预跑缓存静态页）

## 第 15-18 小时｜打磨 + 强制休息

- 只修阻塞演示的 bug，样式问题一律记录不修
- **第 16 小时起：三人轮流睡 3-4 小时**（不睡的话第 20 小时后效率归零，还会改出新 bug）
- A 睡前最后一件事：`git push` + 确认演示缓存已提交

## 第 19-22 小时｜彩排（至少完整走 2 遍）

- **第一遍**：真实 API 完整演示，计时（目标 8 分钟内），记录每个卡点
- **第二遍**：`./dev.sh demo` 演示模式走一遍，确认缓存兜底有效
- 彩排角色：C 主讲、A 操作电脑、B 记录问题
- 22:00 **代码冻结**：只准修致命 bug，任何新功能想都别想

## 第 23-24 小时｜演示

- 提前 30 分钟：重启电脑/浏览器、提前打开页面、再跑一遍 demo 模式自检
- 演示时：**先走真实 API，每一步 A 盯着后台，一旦某步超过 60 秒无响应，立刻切 `./dev.sh demo` 演示模式继续**，解说词："这是我们今早实跑的真实结果"
